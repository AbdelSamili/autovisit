# ADR-003 — Convention de Nommage Package by Layer

## Statut

Accepté

## Contexte

Un projet Java organisé en couches (voir ADR-001) peut structurer ses packages selon deux
conventions distinctes :

- **Package by Layer** : un package par couche technique — `controllers/`, `services/`,
  `repositories/`, `models/` — où chaque package regroupe des classes de toutes les
  fonctions métier partageant le même rôle technique.
- **Package by Feature** : un package par domaine métier — `vehicle/`, `scheduling/`,
  `inspection/`, etc. — où chaque package contient ses propres sous-couches
  (controller, service, repository) limitées à ce domaine.

AutoVisit couvre 9 domaines métier distincts (véhicules, propriétaires, centres et
équipements, contrôleurs, planification/réservation, inspection, procès-verbaux,
assistant IA, notifications), qui vont tous cohabiter dans la même base de code au fil
des 5 sprints. La question à trancher est : quelle convention de nommage adopter pour organiser
les packages de l'application ?

## Décision

AutoVisit adopte la convention **Package by Layer** :
`com.autovisit.{controllers, services, repositories, models}`, plutôt que Package by
Feature.

Ce choix est justifié par trois facteurs.

### 1. Alignement pédagogique

Cette convention est directement héritée de l'enseignement académique reçu, avec un
vocabulaire éprouvé (`controllers`, `services`, `repositories`, `models`) largement
reconnu en entreprise. Elle correspond aux réflexes déjà acquis, ce qui réduit la charge
cognitive de démarrage du projet.

### 2. Validité industrielle confirmée

Package by Layer reste une pratique d'organisation documentée et courante pour des
applications d'entreprise aux besoins bien définis et stables. Ce n'est pas une
convention dépassée : c'est une convention différente de Package by Feature, avec ses
propres compromis, tout aussi légitime pour le contexte d'AutoVisit.

### 3. Simplicité de démarrage

Un seul niveau de dossiers à maintenir mentalement (`controllers/`, `services/`,
`repositories/`, `models/`) plutôt qu'une arborescence par domaine à faire évoluer dès le
Sprint 0, avec une cohérence immédiate avec les réflexes déjà acquis.

## Conséquences

### Coûts acceptés, documentés par avance

**Densité croissante des packages `services/` et `repositories/`.** À mesure que les 9
domaines métier s'accumulent dans les mêmes packages plats, ces deux dossiers concentrent
la majorité des classes du projet. D'après la structure de packages prévue (spec §7.5),
`services/` devrait regrouper environ **24 classes** (VehicleService, OwnerService,
CenterService, EquipmentService, TechnicianService, SlotSearchService, BookingService et
sa chaîne de 5 contraintes, SlotSpecification, InspectionService, CounterVisitService,
InspectionProtocol, ReportService et ses collaborateurs Builder/Template Method,
RagService, AgentService, ToolRegistry, EvaluationHarness, NotificationService), et
`repositories/` environ **14 classes**. Le risque documenté dans la littérature : un
package contenant 20 à 30 classes techniquement homogènes mais métier-hétérogènes devient
difficile à parcourir visuellement, et un changement transversal sur un seul domaine
oblige à naviguer entre plusieurs packages plats plutôt que d'ouvrir un seul dossier de
domaine.

**Frontières de domaine moins visibles dans l'arborescence.** Retrouver « tout ce qui
concerne la planification » demande de filtrer par préfixe de nom de classe
(`Slot*`, `Booking*`) plutôt que d'ouvrir un seul dossier `scheduling/` dédié.

**Risque accru de modèle anémique (voir règle R7).** Sans dossier `business` dédié par
domaine pour rappeler visuellement où doivent vivre les invariants métier, la tentation
de tout pousser dans `services/` plutôt que dans les entités elles-mêmes est plus grande
qu'avec une organisation par domaine.

### Mitigation

- **Discipline de nommage stricte** : chaque classe porte en préfixe le nom de son
  domaine métier (`VehicleService`, `SchedulingService`, etc.), afin de compenser
  partiellement, par la lecture du nom, l'absence de séparation physique en dossiers.
- **Suivi actif de la densité** des packages `services/` et `repositories/` à chaque
  sprint, consigné dans `docs/OBSERVATIONS-LOG.md`.
- **Revue explicite de l'anémie du modèle** en fin de Sprint 1 et de Sprint 3 (spec §17,
  registre des risques) : vérifier que les invariants métier vivent bien dans les
  entités et Value Objects, pas uniquement dans les services.

### Comparaison prévue avec MedTrack

MedTrack (et StockFlow) utilisent une organisation Package by Feature. Cette différence
assumée entre les projets du portfolio est une comparaison **prévue**, pas encore un
résultat observé : elle ne prendra tout son sens qu'une fois les deux bases de code
suffisamment avancées pour être comparées sur des critères concrets (temps de
navigation pour un changement transversal, taille des packages, facilité à localiser un
domaine). `docs/OBSERVATIONS-LOG.md` est le support de cette comparaison au fil des
sprints, plutôt qu'une conclusion arrêtée à l'avance — l'objectif est un point de
discussion directement exploitable en entretien, appuyé sur une expérience vécue des deux
conventions plutôt que sur une préférence théorique.
