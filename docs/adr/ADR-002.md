# ADR-002 — Persistance Polyglotte

## Statut

Accepté

## Contexte

AutoVisit manipule des données de nature très différente :

- des données **relationnelles et fortement structurées** : véhicules, propriétaires,
  centres, lignes, équipements, contrôleurs, rendez-vous — entités avec un schéma stable,
  des relations explicites, et des contraintes d'intégrité fortes (unicité de
  l'immatriculation, du VIN, cohérence des références entre entités).
- des données **documentaires à structure variable** : le procès-verbal d'inspection. Le
  nombre et la nature des points contrôlés dépendent de la catégorie du véhicule (une
  moto ne partage pas les points de contrôle d'un poids lourd), et chaque point porte un
  résultat, une gravité, des mesures optionnelles et des observations libres — un schéma
  qui varie d'un document à l'autre par nature, pas par accident.
- des données **volatiles et consultées à haute fréquence** : résultats de recherche de
  créneaux disponibles, données de session — pour lesquelles la latence prime sur la
  durabilité.

Faire porter ces trois profils de données par une seule technologie de persistance
imposerait des compromis coûteux dans au moins un des trois cas. La question à trancher
est donc : quelle(s) technologie(s) de persistance adopter, et selon quelle frontière de
responsabilité entre elles ?

## Décision

AutoVisit adopte une persistance polyglotte à trois technologies, chacune répondant à un
profil de données distinct :

| Technologie    | Rôle                                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **PostgreSQL** | Données relationnelles : véhicules, propriétaires, centres, lignes, équipements, calibrations, contrôleurs, qualifications, rendez-vous, identité et état de l'inspection |
| **MongoDB**    | Contenu du procès-verbal d'inspection (document à structure variable)                                                                                                     |
| **Redis**      | Cache-aside sur les recherches de créneaux disponibles, sessions                                                                                                          |

### Justification précise de MongoDB pour le procès-verbal

Modéliser le procès-verbal en relationnel imposerait l'une de ces deux approches, toutes
deux insatisfaisantes :

- une table de valeurs génériques de type **EAV (Entity-Attribute-Value)** — un
  anti-pattern connu, qui sacrifie l'intégrité du schéma et la lisibilité des requêtes
  pour gagner en flexibilité ;
- une **explosion de colonnes nullables** couvrant l'union de tous les points de contrôle
  possibles pour toutes les catégories de véhicules, dont la majorité serait `NULL` pour
  n'importe quel PV donné.

Le document est ici la forme naturelle : un procès-verbal est intrinsèquement un
agrégat cohérent (identification du véhicule, liste de points avec résultats, résultat
global, échéance de contre-visite éventuelle) qui n'est jamais interrogé point par point
à travers l'ensemble des PV — il est toujours lu et écrit comme un tout, pour une
inspection donnée. C'est exactement le cas d'usage pour lequel un document JSON stocké
tel quel évite l'un ou l'autre anti-pattern relationnel ci-dessus.

### Frontière stricte entre PostgreSQL et MongoDB

La frontière de responsabilité entre les deux bases est absolue et non négociable :

- **MongoDB stocke exclusivement le contenu du PV** : la liste des points contrôlés, leurs
  résultats, gravités, mesures et observations.
- **PostgreSQL conserve l'identité, l'état et les références** de l'inspection :
  `inspection_id`, `result` (résultat global dérivé), `pv_document_id` (référence vers le
  document MongoDB correspondant).

**L'état de l'inspection ne vit jamais dans MongoDB.** La machine à états de l'inspection
(SCHEDULED → IN_PROGRESS → PASSED / FAILED_MAJOR / FAILED_CRITICAL → ... voir spec §7.7)
est portée intégralement par PostgreSQL. MongoDB ne fait que documenter le détail d'un
résultat déjà déterminé côté relationnel — il n'est jamais la source de vérité de l'état.

### Ordre d'écriture documenté

Il n'existe pas de transaction atomique entre PostgreSQL et MongoDB : ce sont deux
systèmes de stockage indépendants. L'ordre d'écriture est donc une règle métier explicite,
et non un détail d'implémentation laissé à l'appréciation du développeur :

> **Le document PV est écrit dans MongoDB avant le commit de la transaction PostgreSQL
> portant `pv_document_id`.**

Conséquence de cet ordre en cas d'échec partiel :

- Si l'écriture MongoDB réussit puis que le commit PostgreSQL échoue : un **document PV
  orphelin** dans MongoDB est toléré temporairement, puis nettoyé par un **job de
  réconciliation**.
- L'inverse est strictement interdit : **une inspection PostgreSQL référençant un
  `pv_document_id` inexistant dans MongoDB n'est jamais un état acceptable du système.**

Le raisonnement derrière ce choix : un document orphelin dans MongoDB est une donnée
inerte, sans conséquence fonctionnelle tant que rien ne le référence — il est simplement
nettoyé plus tard. Une référence PostgreSQL vers un document absent est en revanche une
incohérence active : toute lecture du PV échouerait pour une inspection que le système
considère pourtant comme clôturée. C'est cette asymétrie de risque qui dicte le sens de
l'ordre d'écriture.

## Conséquences

### Coûts acceptés

- **Deux technologies de persistance à maintenir** : deux moteurs, deux modèles
  mentaux, deux surfaces d'exploitation.
- **Deux jeux de tests d'intégration distincts** (PostgreSQL et MongoDB via
  Testcontainers), plutôt qu'un seul.
- **Absence de transaction atomique entre les deux bases**, compensée par l'ordre
  d'écriture documenté ci-dessus et un job de réconciliation pour les documents orphelins
  — pas par une garantie transactionnelle native.

### Bénéfices obtenus

- Chaque profil de données est porté par la technologie qui lui correspond nativement,
  sans anti-pattern de contournement (EAV, colonnes nullables massives).
- La frontière stricte entre les deux bases rend le système auditable : on sait toujours,
  sans ambiguïté, quelle base fait autorité sur quelle donnée.
- La règle d'ordre d'écriture, documentée à l'avance, transforme une question
  d'entretien difficile (« que se passe-t-il si une écriture échoue ? ») en une réponse
  déjà préparée et justifiée.
